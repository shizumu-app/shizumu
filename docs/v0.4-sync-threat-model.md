# v0.4 sync threat model

Scope: the sync engine that ships in v0.4 (`src-tauri/src/sync/`) and
its self-deploy relay (`shizumu-relay/`). The writing surface itself
is local-only and outside this document.

The sync engine encrypts every op the user emits on the device, hands
the ciphertext to a relay the user controls, and lets every other
device on the same account fold those ops back into its local state.
The relay never sees prose. This document enumerates what it does see,
what it cannot, and the threats v0.4 does not address.

Companion: `docs/v0.4-sync-security-audit.md` is the point-in-time
vulnerability review. This threat model has been reconciled with its
findings; finding IDs (C1, H1-H5, M1-M5) are cited inline below.

## What the user controls

- **The 24-word BIP-39 phrase.** 256 bits of entropy generated by
  `OsRng` and turned into the user's signing / kex / content / meta
  keys via PBKDF2-HMAC-SHA512 → HKDF-SHA256. See
  `src-tauri/src/sync/keys.rs::user_keys_from_phrase`. Possession of
  the phrase is possession of the account, past and future.
- **The relay.** Either self-hosted (the default v0.4 posture) or run
  by a trusted operator. The trust model assumes the user can verify
  the relay binary is the unmodified one published by the shizumu
  project.

## What the relay sees (the leak surface)

Per-op data on the wire and at rest in the relay's `log` table:

- **Ciphertext blobs.** XChaCha20-Poly1305 over the JSON op payload,
  keyed by `content_master_key`. See
  `src-tauri/src/sync/envelope.rs::encrypt_op`. Each blob includes a
  random 24-byte nonce, the AEAD tag, and the ciphertext of `(op_id ||
  payload_json)`.
- **`op_kind` (plaintext).** One of `page_blob`, `pin_op`,
  `setting_op`, `page_yjs`, `lineage_op`, `tombstone`. The relay uses
  this to know which lane / stream prioritization to apply, so it
  cannot be encrypted without losing prioritization.
- **`stream_id` (plaintext).** One of three lanes (0 = settings /
  lineages / pins, 1 = discrete pages, 2 = continuous yjs). Same
  reasoning as op_kind.
- **`user_seq` (plaintext).** Monotonic per-user counter the relay
  assigns on commit. Reveals total op count for the account.
- **`blob_size` (plaintext).** Byte length of the ciphertext.
  Plaintext sizes are deterministic (size = ciphertext - 24 nonce - 16
  tag bytes), so this leaks payload size.
- **`doc_id_ct` (HMAC of doc_id under `meta_key`).** Same logical doc
  → same 32-byte ct, opaque to the relay. See
  `src-tauri/src/sync/envelope.rs::doc_id_ct`. The relay can count
  ops per ct but cannot map ct back to a plaintext doc_id.
- **Device signing pubkeys + Ed25519 signatures on requests.** The
  authentication and integrity primitive. See
  `src-tauri/src/sync/signing.rs::sign_request` and
  `shizumu-relay/src/auth.rs::verify`.
- **IP addresses + request timing.** Whatever the transport layer
  surfaces. The relay logs may retain these.
- **TLS-level metadata.** Handshake, SNI, certificate chain.

## What the relay does NOT see

- Prose content (encrypted under `content_master_key`).
- Pin titles, pin content, pin annotations (same).
- Lineage names, lineage modes (same).
- Settings values (same).
- The plaintext mapping from any specific page / pin / lineage to its
  `doc_id_ct`. The HMAC is one-way for the relay because it lacks
  `meta_key`.

## What an attacker with access to the relay can do

Assume the relay's host is compromised: file system, process memory,
SQLite db, blob store, request logs. Without breaking AEAD or
recovering one of the user's secret keys, the attacker can:

- Count ops per hour / day per user. The activity-pattern leak: when
  the user writes most, when they're silent, gap structure.
- See which `doc_id_ct` values are most frequently updated. A
  continuous trail under active editing stands out as a single ct
  with steady-cadence `page_yjs` ops. The attacker doesn't know which
  trail it is, but they know one trail is "the big one."
- See proportions: page vs pin vs setting ops. Infers writing style
  (pin-heavy vs free-form, etc).
- See `user_seq` and infer total op count for the account.
- Stall, drop, or refuse requests (denial of service).
- Track distinct device signature key prefixes to count active
  devices and time-of-day usage per device.
- Replay, reorder, withhold, or roll back the op stream it serves to a
  device. Ops carry no per-op author signature in v0.4, so a device
  authenticates a pulled op only by AEAD under the shared
  `content_master_key` (which proves a key-holder produced the blob,
  not which device, nor freshness or ordering). See the security audit
  finding C1 in `docs/v0.4-sync-security-audit.md`. Mitigations now in
  place: ops are content-addressed by `op_id` (PRIMARY KEY) so a
  replay is an idempotent no-op; per-row `applied_hlc_ts` gating blocks
  stale-resurrect; and an implausibly-future HLC from a pulled op is
  demoted to 0 rather than allowed to win every future merge
  (`pull.rs`). The full fix (per-op Ed25519 author signatures, verified
  against the user-key-authorized device set, rejecting revoked
  authors) is a v0.5 wire-protocol change tracked as C1.
- Re-serve ops from a revoked device. Revocation is enforced relay-side
  (the relay refuses that device's signed requests), but a malicious
  relay can still replay a revoked device's previously-uploaded ops
  until per-op author authentication (C1) lands. Note that a revoked or
  lost device also keeps `content_master_key` and can decrypt any op it
  obtains until key rotation (v0.5).

## What an attacker with access to the relay CANNOT do (without breaking AEAD)

- Read any prose, pin content, lineage name, or setting value.
- Alter the *contents* of an op without invalidating the AEAD tag
  (which the receiving device verifies during `decrypt_op`). Note this
  protects each blob's integrity, NOT the freshness, ordering, or
  authorship of the stream: replay / reorder / rollback are listed
  above as things the relay CAN do until C1 lands.
- Fabricate brand-new op contents. Producing a blob that decrypts
  requires `content_master_key`, which the relay never holds.
- Forge signed requests as the user. Per-request signatures use the
  device's Ed25519 key, not anything the relay holds. See
  `src-tauri/src/sync/signing.rs`. Captured signed requests cannot be
  replayed: the relay binds a `(device_id, nonce)` to a persisted
  used-nonce table (survives restart) and enforces a +/-5min timestamp
  window.
- Downgrade the transport. The client rejects any relay URL that is not
  `https://` (loopback `http://` excepted for local self-host); see
  `config::validate_relay_url`.
- Cross-correlate users. Each user's `meta_key` is independent (HKDF
  out of a per-account seed), so `doc_id_ct` values do not match
  across accounts even when the underlying doc_id strings would.

## What an attacker with access to a single device can do

- Read every page, pin, lineage, and setting on that device. The
  local database is the source of truth; encryption is only at rest
  via OS keyring + (optional) at-rest db key. Caveat: when the OS
  keyring is unavailable (e.g. KDE/Fedora), the account secrets fall
  back to plaintext rows in the local DB. v0.4 no longer does this
  silently: `sync_status` reports `keys_at_rest_unprotected` so the UI
  can warn the user (security audit H3).
- Sign new ops as that device until the user revokes it. The relay
  accepts any request signed by a known device key.
- Pull every op the user has ever made (the device has
  `content_master_key`).

Mitigation: `revoke_device` from any other device on the account.
The relay refuses subsequent requests from the revoked device's key
and removes it from the device list.

## What an attacker with access to the recovery phrase can do

- Re-derive `user_sign_priv`, `user_kex_priv`, `content_master_key`,
  and `meta_key`. The phrase IS the account.
- Enroll a fresh device on the relay (the signed `authorized_sig` is
  reproducible).
- Decrypt every op the relay holds, past and future, including ops
  the user will emit tomorrow as long as the same `content_master_key`
  is in use.

This is by design. The phrase is the only recovery contract; there is
no separate account-recovery email / SMS / second factor. v0.5 spec
work covers key rotation so phrase compromise does not implicate ops
post-rotation, but v0.4 does not have that.

## Trust model

- **Relay: honest-but-curious.** Forwards ciphertext faithfully but
  may observe metadata. The user is expected to either run their own
  relay or trust the operator the way they'd trust a paid hosting
  provider with an end-to-end-encrypted mailbox.
- **Relay operator: the user (self-host) or a named trusted party.**
- **Device: trusted while in user's possession.** The lock screen,
  full-disk encryption, and OS keyring are the line of defense.
- **Lost device: mitigated by `revoke_device` from any other device.**
  The lost device retains read access to whatever it had at loss
  time, but can no longer pull new ops or sign requests.

## Addressed in v0.4 by key rotation (audit C1 + forward secrecy)

v0.4 implements **content-key epoch rotation** (`src-tauri/src/sync/epoch.rs`,
`rotation.rs`) and **per-op author signatures** (`op_auth.rs`). Together:

- **Revocation actually bites.** Revoking a device generates a new epoch
  secret `ES_{e+1}` (random, not phrase-derived), wraps it to every
  remaining device's per-device X25519 key (and a phrase-recovery key),
  and bumps the account epoch. New ops are encrypted under the new epoch's
  content key, which the revoked device never receives — so it is locked
  out of all content from epoch e+1 onward (read and write).
- **Per-op author authentication (C1).** Each op carries, inside the AEAD
  blob, its author device's signing pubkey, an op signature, and the
  author's attestation under the op's epoch user-signing key. Receivers
  verify the chain against the epoch user-sign key they derive locally —
  no relay trust. A revoked device can't forge a valid attestation for any
  post-rotation epoch (it lacks that epoch's secret). Combined with `op_id`
  content-addressing and `applied_hlc_ts` gating, replay/reorder/rollback
  of a revoked device's ops no longer affects a current device.
- **Recovery contract preserved.** Each epoch secret is also wrapped to a
  phrase-derived recovery key, so the phrase alone still recovers every
  epoch after total device loss (`recover_epoch_keys_from_phrase`).

Residual (still true): **phrase compromise is total** — whoever holds the
phrase can derive the recovery key and unwrap every epoch. Rotation defends
device loss, NOT phrase loss; a phrase leak means starting a new account.
Verification status: covered by unit tests both repos; the multi-device
revoke-lockout **e2e** runs on the dev box (relay subprocess required).

## Threats NOT addressed in v0.4
- **Metadata leak via op_kind / stream_id.** Documented above.
  Encrypting these costs the relay its bandwidth prioritization; the
  v0.5 spec evaluates the tradeoff.
- **DoS by a malicious relay.** Out of scope. Self-host or trust your
  operator. A user who cannot trust their relay should not be using
  this sync engine.
- **Side channels (timing, traffic analysis).** Out of scope. The
  relay sees request timing and blob size; the network sees TLS
  envelope timing. Padding ops to fixed sizes would help; v0.4 does
  not do this.
- **Pre-quantum.** The pipeline is BIP-39 → HKDF-SHA256 →
  Ed25519 / X25519 / XChaCha20-Poly1305. All pre-quantum primitives.
  A future PQ migration would replace Ed25519 and X25519.
- **Pair-token entropy.** Four words from a 256-word list = 32 bits
  of entropy. The relay now bounds online guessing with a per-token
  failed-attempt cap (independent of IP) and only honors a proxy's
  forwarded client IP when the peer is in the configured
  trusted-proxy set, so a rotating `X-Real-IP` no longer buys fresh
  rate-limit buckets (security audit H4). Widening the token to >= 64
  bits is deferred because it is a cross-repo client change.
- **Compromise of the host where the relay binary runs.** The
  attacker gets everything in "What an attacker with access to the
  relay can do" above. There is no fallback if the operator's host
  is rooted.
- **Cross-device de-anonymization via signing-key reuse.** A user who
  enrolls the same device on two different relays under two
  different identities is identifiable across the two by the
  device's public signing key. v0.4 does not generate fresh
  device-signing keys per relay binding.

## Responsible disclosure

Security issues should be reported privately. Open a GitLab issue
marked confidential, or email `hello@shizumu.app` with `SECURITY` in
the subject line. See [SECURITY.md](../SECURITY.md) for scope and
response times.

Please include:

- The affected file(s) and a minimal reproduction.
- Whether the issue is exploitable against a stock self-hosted relay
  or only against the hosted variant.
- The version / commit hash of the client and relay you tested.

We commit to acknowledging reports within seven days and to publishing
a fix or mitigation timeline within thirty days of acknowledgement.
